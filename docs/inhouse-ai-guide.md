## 1. 기능 요구사항
요구사항을 바꾸는 변경은 임의로 하지 않는다. 바꿔야 하면 이유를 담당 프로에게 먼저 알린다.

### 1-1. 대화와 AI 동작
| ID | 요구사항 | 상태 | 확인 방법 |
|---|---|---|---|
| F-01 | AI는 실행 전에 작업 흐름을 제안하고 사용자 승인을 받은 뒤 실행한다 | 구현 | `test_flow_lifecycle`, 데모 |
| F-02 | **사용자에게 묻는 것을 최소로 한다.** 빠진 조건은 기본값을 정해 흐름의 단계 설명에 적고 진행한다. 진행할 수 없을 때만 한 번에 모아 묻는다 | 구현·실제 AI 미확인 | 조건이 빠진 요청을 보내 질문 없이 흐름이 나오는지 본다 |
| F-03 | **대화에 사람이 볼 필요 없는 정보를 쓰지 않는다.** 답변은 3~5줄(한 일, 핵심 숫자, 다음 권고). 경로·ID·툴 이름·JSON·진행 중계 금지 | 구현·실제 AI 미확인 | 실제 AI 답변을 읽어 본다 |
| F-04 | AI의 생각과 툴 호출은 대화에서 "작업 N건" 한 줄로 접는다. 눌러야 자세히 보인다 | 구현 | 스모크 |

규칙의 원본은 `agent-context/INSTRUCTIONS.md` 0-1절이다.

### 1-2. 작업 흐름 탭
| ID | 요구사항 | 상태 | 확인 방법 |
|---|---|---|---|
| F-10 | 흐름도는 **위에 고정**하고, 아래 단계별 결과만 스크롤한다 | 구현 | 데모 |
| F-11 | 작업 흐름의 결과 전체를 흐름도 아래에 단계 순서대로 펼친다 | 구현 | 데모 |
| F-12 | 흐름도의 단계를 누르면 그 단계 결과로 스크롤한다 | 구현 | 데모 |
| F-13 | **'1단계, 2단계' 번호가 흐름도·결과·대화 카드·보고서에서 같다.** 규칙은 위상 정렬(`flow/order.ts`, `report.order_nodes`). 둘을 함께 고친다 | 구현 | `test_step_order_and_body_split` |
| F-14 | AI는 결과를 게시할 때 `flow_id`·`node_id`를 넣는다. 없으면 '단계에 묶이지 않은 결과'로 간다 | 구현·실제 AI 미확인 | 실제 AI 작업 뒤 '기타' 구역이 비어 있는지 본다 |

### 1-3. 보고서 탭
결과 탭은 없앴다. 다시 만들지 않는다. 결과는 작업 흐름 탭에서 본다.

| ID | 요구사항 | 상태 | 확인 방법 |
|---|---|---|---|
| F-20 | 보고서는 결과를 모은 것이 아니라 **AI가 결과와 작업 내용을 해석해 새로 쓴 문서**다 | 구현·실제 AI 미확인 | 실제 AI 보고서에 해석·결론·권고가 있는지 읽어 본다 |
| F-21 | **'AI 보고서 작성' 버튼**을 누르면 최신 결과로 다시 쓰고 새 판이 쌓인다. 이전 판을 고를 수 있다 | 구현 | `test_ai_report`, 데모 |
| F-22 | 보고서를 쓴 뒤 결과가 새로 생기거나 바뀌면 그 수를 알리고 다시 쓰기를 권한다 | 구현 | `test_ai_report` |
| F-23 | 본문에 그림·표를 넣고 '그림 1.', '표 1.' 번호를 자동으로 붙인다(`![캡션](artifact:<id>)`) | 구현 | `test_ai_report` |
| F-24 | Word·HTML은 화면과 같은 내용이다 | 구현 | `test_ai_report` |

### 1-4. 데이터 탭과 Output 추가
| ID | 요구사항 | 상태 | 확인 방법 |
|---|---|---|---|
| F-29-1 | **Simulator 탭:** 대화와 결과를 그대로 둔 채 캔버스 안에서 예측한다. 데이터 탭과 분리한다 | 구현 | 스모크 |
| F-29-2 | **모델 버전:** Simulator는 스터디 하나, 모델은 그 버전이다. 현재 버전은 하나이고 되돌릴 수 있다. 공유 링크와 3D 모델이 현재 버전을 따라간다 | 구현 | `test_simulators.py` |
| F-29-3 | **Simulator 목록(`/simulators`):** 내 것과 공유받은 것만 모아 프로젝트 없이 바로 연다. 링크를 한 번 열면 자동으로 들어온다 | 구현 | `test_simulators.py`, 스모크 |
| F-30 | **입력(Input)과 출력(Output)을 나눠 보여 준다.** 케이스 표 머리글도 입력·출력으로 묶는다 | 구현 | 데모 |
| F-31 | **언제든 Output을 추가할 수 있다.** 이미 해석한 케이스는 해석을 다시 돌리지 않고 추출해 기존 결과에 합친다 | 구현(실제 툴 추출은 미확인) | `test_add_output_extracts_existing_and_later_cases` |
| F-32 | 이후 케이스에서도 계속 추출한다. 추가할 때 실행 중이던 케이스도 끝나는 대로 뽑는다 | 구현(실제 툴 추출은 미확인) | 같은 테스트, `test_post_steps_merge_and_extract_existing` |
| F-33 | 추출이 실패해도 해석 결과와 케이스 상태(complete)는 그대로 두고, 오류를 알린다 | 구현 | 코드 `_on_extracted` |

### 1-5. 해석 데이터 저장 (HDF5)
| ID | 요구사항 | 상태 | 확인 방법 |
|---|---|---|---|
| F-40 | CAE 데이터는 **HDF5(case.h5)로 압축해 저장**한다. 케이스 하나에 파일 하나, 기본은 손실 없는 압축 | 구현 | `test_h5store.py` |
| F-41 | **해석 결과 데이터를 빠짐없이 저장한다.** 케이스 폴더의 모든 파일을 담았음·원본만 남음·제외로 목록에 남기고, 묶은 뒤 다시 읽어 검증한다 | 구현 | `test_pack_case_keeps_everything` |
| F-42 | 결과 파일 내용 전체(모든 스텝·프레임·필드)를 담는 추출 단계를 쓴다: LS-DYNA `dyna_to_h5.py`, Nastran·OptiStruct `op2_to_h5.py`, Abaqus `abq_odb_to_npz.py` | 구현·실제 툴 미확인 | [onsite-validation.md](onsite-validation.md) 방식으로 사내 결과 파일에서 시험 |
| F-43 | 크기 기준(`upload_max_mb`, 기본 500) 이하는 서버에 올리고, 넘으면 PC에만 두고 정보만 보낸다 | 구현(큰 파일은 미확인) | `test_archive.py`, 큰 모델로 시험 |
| F-44 | 원본이 지워져도 case.h5로 3D 학습과 Output 추가를 다시 할 수 있다 | 3D 학습만 구현. Output 추가는 추출 스크립트를 case.h5에서 읽게 작성해야 한다 | `test_case_archive_saved_and_used` |

| ID | 요구사항 |

| Simulator 탭 | 버전 표시(눌러서 표를 편다), 공유, 넓게 보기, 예측 화면. 패널이 좁으면 한 줄로 쌓는다 |
| 설정 | 왼쪽 제목·설명, 오른쪽 내용, 구획 사이 옅은 선 |

## 3. 일하는 방식
### 3-1. 변경할 때마다
| 바꾼 것 | 실행 | 통과 기준 |
|---|---|---|
| Python | `.venv\Scripts\python -m pytest server/tests agent/tests -q` | 모두 passed |
| 프론트엔드 | `cd frontend; npm run build` | 오류 없음 |
| 화면·흐름 | 서버를 띄운 뒤 `cd frontend; npm run smoke -- --demo` | 마지막 줄 `PASS` |
| 스킬 스크립트 | `python -m py_compile <파일>` | 오류 없음 |

- 화면을 바꿨으면 `frontend\e2e\shots\` 스크린샷을 **밝은·어두운 테마 모두** 직접 열어 겹침·잘림·빈 화면을 확인한다. 스모크는 밝은 테마만 찍으므로 어두운 테마는 따로 확인한다.
- 눌러야 보이는 메뉴·모달도 확인한다. 자동 점검이 지나가지 않는다.
- 테스트가 실패하면 원인을 고친다. 테스트를 지우거나 약하게 만들어 통과시키지 않는다.

### 3-2. 지켜야 할 규칙
- PC Agent·MCP·스킬을 바꾸면 `agent/dds_agent/__init__.py`의 `__version__`을 올리고, 관리 > Agent 배포로 배포한다.
- 서버 API를 바꾸면 `schemas.py`와 테스트를 함께 고친다. PC Agent 메시지는 `main.py handle()`과 서버 쪽을 짝으로 맞춘다.
- 새 MCP 툴은 `frontend/src/chat/labels.ts`에 쉬운 이름을 넣고 `agent-context/INSTRUCTIONS.md`에 사용법을 적는다.
- 커밋 메시지는 한국어로, 첫 줄은 요약, 본문은 "- " 목록으로 쓴다. 검증을 통과한 뒤 커밋한다. 푸시는 담당 프로가 요청할 때 한다.
- 기능이나 화면 규칙을 바꾸면 `product-spec.md`와 이 문서도 함께 고친다.

### 3-3. 하지 않을 것
- 결과 탭 되살리기, 같은 기능의 버튼 중복, 대화에 결과 표·경로 다시 쓰기
- 실제 툴에서 확인하지 않은 API를 확인된 것처럼 쓰기(`TODO(사내검증)`을 달고 알린다)
- 해석이 맞는지 AI가 혼자 판단하기: 결과가 물리적으로 맞는지는 엔지니어가 판단한다
- 원본 모델 파일 덮어쓰기, 케이스 폴더 밖에 결과 흩뿌리기
- 외부 인터넷에서 무언가 받기
- 표시한 상태를 부풀리기: 데모로만 본 것을 "실제로 동작함"이라고 보고하지 않는다

### 3-4. 끝나면 이렇게 보고한다
1. 무엇을 바꿨는가(요구사항 ID가 있으면 함께)
2. 무엇으로 확인했는가(명령과 결과). 실제 툴·실제 AI로 확인한 것과 데모로만 확인한 것을 나눈다
3. 확인 못 한 것과 담당 프로가 할 일
